# KICS 2026 논문 반영용 정량 결과

최초 작성: 2026-09-23 / STT 다화자 결과 갱신: 2026-09-26

이 문서는 Windows 논문 편집 환경으로 전달할 정량 결과의 단일 요약본이다.
각 수치는 별도 원시 결과와 해시로 보존되어 있으며, 서로 다른 평가셋의
점수를 임의로 합산하지 않는다.

## 1. 명령 계획 성능

40개 요구사항 기반 고정 평가셋의 exact match 결과는 다음과 같다.

| 조건 | 전체 | 동작 필요 | No-op |
| --- | ---: | ---: | ---: |
| LLM Only | 8/40 (20.0%) | 5/22 (22.7%) | 3/18 (16.7%) |
| LLM + Context | 8/40 (20.0%) | 6/22 (27.3%) | 2/18 (11.1%) |
| Rules Only | 31/40 (77.5%) | 13/22 (59.1%) | 18/18 (100.0%) |
| Full Pipeline | 37/40 (92.5%) | 20/22 (90.9%) | 17/18 (94.4%) |

동일 조건을 5회 반복했을 때 네 조건의 전체 exact match와 case별 성공/실패가
모두 동일했다. Full Pipeline은 매회 37/40이었으며 실패 case는 C03, C09,
C34로 고정됐다.

## 2. Prospective Generalization

생산 코드를 고정한 뒤 새로 작성하고 결과 관측 전에 freeze한 20개 평가셋의
첫 실행 결과다.

| 조건 | 전체 | 동작 필요 | No-op |
| --- | ---: | ---: | ---: |
| LLM Only | 6/20 (30.0%) | 4/13 (30.8%) | 2/7 (28.6%) |
| LLM + Context | 5/20 (25.0%) | 4/13 (30.8%) | 1/7 (14.3%) |
| Rules Only | 10/20 (50.0%) | 3/13 (23.1%) | 7/7 (100.0%) |
| Full Pipeline | 13/20 (65.0%) | 8/13 (61.5%) | 5/7 (71.4%) |

이 결과는 기존 요구사항 평가보다 새로운 표현에 대한 성능이 낮음을 보여준다.
따라서 92.5%는 고정 요구사항 집합 성능으로, 65.0%는 별도의 prospective
일반화 점검 결과로 구분해서 제시해야 한다.

## 3. STT 및 음성 명령 경로

고정된 영어 명령 12개를 화자당 3회씩 녹음했다. 최초 실험은 MacBook 내장
마이크를 사용한 1명(36개), 후속 실험은 별도 수집 경로를 사용한 3명(108개)이다.
두 실험 모두 `faster-whisper tiny.en` CPU/int8과 동일한 고정 명령 평가셋을
사용했다. 후속 실험에서는 원본 108개가 모두 디코딩되고 평가 가능했으며
기술적 사유로 제외된 녹음은 없었다. 전체 144개 합계는 설명적 수치이고,
서로 다른 수집 프로토콜의 화자를 하나의 통제 실험으로 간주하지 않는다.

| 지표 | 최초 1명 (36개) | 후속 3명 (108개) | 설명적 전체 (144개) |
| --- | ---: | ---: | ---: |
| Corpus WER | 22/216 (10.2%) | 91/648 (14.0%) | 113/864 (13.1%) |
| 정규화 transcript 완전 일치 | 22/36 (61.1%) | 64/108 (59.3%) | 86/144 (59.7%) |
| 음성 입력에서 gold command까지 exact match | 30/36 (83.3%) | 82/108 (75.9%) | 112/144 (77.8%) |
| 텍스트 기준 command 보존 | 33/36 (91.7%) | 91/108 (84.3%) | 124/144 (86.1%) |

WER은 기준 문장 단어 수 대비 삽입·삭제·대치 단어 수이고, command exact
match는 최종 명령과 고정 정답의 일치율이다. 텍스트 기준 command 보존은
같은 문장의 텍스트 입력으로 생성한 계획과 음성 입력 계획의 일치율이므로
정답 정확도와 다르다. 설명적 전체에서 동작 필요 명령은 88/120 (73.3%),
no-op은 24/24 (100.0%)였다. 따라서 전체 77.8%만 단독으로 제시하지 않는다.

후속 화자별 WER은 5.1~26.4%, 음성-정답 명령 일치율은 58.3~88.9%로
변동이 컸다. 발음 또는 억양이 원인일 가능성은 있으나, 각자의 발음 수준,
마이크, 방 소음, 녹음 조건을 독립적으로 평가하지 않아 원인을 확정할 수 없다.
낮은 점수를 확인한 뒤 특정 화자를 제외하면 성능을 과대평가하게 되므로
논문용 집계에는 모든 평가 가능 녹음을 포함했다. 화자별 원자료와 감사
결과는 [후속 STT 결과](multispeaker-stt-results-2026-09-26.md) 및
[4화자 감사](four-speaker-stt-audit-2026-09-26.md)에 보존한다.

논문 본문용 문장: "고정된 12개 영어 명령을 화자당 3회 입력한 후속 3화자
평가(108개)에서 corpus WER은 14.0%, 음성 입력의 최종 명령 exact match는
75.9%였다. 초기 1화자 평가(36개)는 각각 10.2%, 83.3%였으며, 수집
방식이 달라 결과를 별도 보고하였다. 후속 화자 간 성능 편차가 관찰됐으나
표본과 녹음 환경 정보가 제한되어 그 원인을 특정할 수 없다."

## 4. 지연시간

6회 warm-up 후 6개 대표 case를 30회 순환 측정한 command-planning 지연시간은:

| 지표 | 최초 측정 | 자원 프로파일 동시 측정 |
| --- | ---: | ---: |
| 평균 | 3215.826 ms | 3007.444 ms |
| 중앙값 | 2923.703 ms | 2754.406 ms |
| P95 | 4967.947 ms | 4577.386 ms |

두 측정 모두 STT, Home Assistant 상태 수집, 네트워크, Matter, IR, 물리 장치
settling time을 포함하지 않는 warm software command-planning latency다.

STT 평가에서 faster-whisper 전사 시간은 평균 285.010 ms, 중앙값 216.709
ms였다. 첫 전사에는 모델 초기화가 포함되므로 strict warm-only 값은 아니다.

### 4.1 물리 종단간 커튼 확인

고정 WebM 음성 파일을 실제 `/api/command/audio` 경로에 입력한 커튼 열기·닫기
각 3회, 총 6회에서 기대 명령과 Home Assistant 최종 커튼 상태가 모두 일치했다.
API 응답시간 평균은 20,838.821 ms, API 응답 이후 상태 확인까지 포함한 커튼
settle 시간 평균은 20,884.520 ms였다. 이 값은 고정 파일 업로드, STT, live
context, LLM, Home Assistant, Matter 경로를 포함하지만 브라우저 녹음·발화 시간과
외부 카메라 기반 물리 완료 시점은 포함하지 않는다.

IR 에어컨은 `AC Off` 한 번 뒤 `AC Cool 24` 한 번의 시작 명령과, `AC Off` 한 번의
종료 명령을 각각 사용자 육안으로 확인했다. 다만 각 1회 acceptance 관찰이며 IR의
양방향 상태 피드백이 없으므로 반복 신뢰도나 물리 지연시간 결과로 제시하지 않는다.

## 5. MacBook Air M1 자원 사용

`llama3.2:3b`를 preload한 뒤 동일한 30회 workload를 0.5초 간격으로 측정했다.

| 지표 | 결과 |
| --- | ---: |
| Ollama RSS 평균 / 최대 | 2480.331 / 2494.422 MB |
| Python workload RSS 평균 / 최대 | 24.504 / 38.000 MB |
| 합산 monitored RSS 평균 / 최대 | 2504.835 / 2522.328 MB |
| CPU 평균 / P95 / 최대 | 18.021 / 55.200 / 68.600% |
| loaded-idle memory-pressure free 중앙값 | 20% |
| workload 최저 memory-pressure free | 17% |

RSS는 Apple 통합 메모리 전체를 정확히 나타내지 않는 process proxy다. CPU 100%
는 논리 코어 하나 기준이며 GPU 사용률은 측정하지 않았다. 따라서 논문에서는
“통합 메모리 사용량 2.52 GB”가 아니라 “모니터링한 프로세스 RSS 최대 약
2.52 GB”라고 표현해야 한다.

## 6. 논문에 사용할 수 있는 결론

- 로컬 3B 모델 단독 출력보다 normalization, context policy, schema validation,
  physical allow-list를 결합한 Full Pipeline의 고정 요구사항 정확도가 높았다.
- 동일 환경 5회 반복에서 case-level 결과가 변하지 않아 해당 설정에서의
  반복 안정성이 확인됐다.
- prospective set 성능 저하는 새로운 표현에 대한 일반화가 남은 한계임을
  보여준다.
- 후속 3화자에서 음성 입력의 최종 명령 일치율은 75.9%였고, 화자별 편차가
  확인됐다. 소규모 편의 표본이며 화자 독립 성능이나 억양 효과로 일반화할
  수 없다.
- 8 GB M1 환경에서 고정 workload가 완료됐으며, 측정된 프로세스 RSS와 시스템
  memory pressure 범위 안에서 실행 가능성을 확인했다.

## 7. 사용하면 안 되는 표현

- “모든 자연어 명령에서 92.5% 정확도”
- “화자와 환경에 관계없이 83.3% 음성 명령 정확도”
- “성능이 낮은 화자를 제외한 수치를 전체 다화자 성능으로 보고한다”
- “한국어 모국어 화자의 영어 억양 때문에 오류가 발생했다”
- “LLM이 2.52 GB의 통합 메모리를 사용한다”
- “CPU 사용률이 최대 68.6%이므로 전체 시스템 자원이 31.4% 남는다”
- “물리 장치까지 평균 3초 안에 동작한다”
- “IR 에어컨의 실제 상태를 Home Assistant가 확인했다”

각 문장은 현재 측정 범위를 넘어선다.
