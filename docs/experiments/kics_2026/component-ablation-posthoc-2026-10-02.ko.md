# 후처리 구성요소 사후 재생 분석

분석일: 2026-10-02

## 목적과 범위

기존 40건 요구사항 평가와 20건 prospective 평가의 **보존된 첫 실행 LLM
원출력**을 동일한 생산 후처리 함수에 재입력했다. 새로운 LLM 호출, 프롬프트
변경, 정답 수정, Home Assistant 명령 전송은 없었다. 이것은 고정 원출력의
후처리 기여를 살피는 **사후 재생 분석**이지, 각 구성요소를 제거한 상태에서
모델을 다시 추론한 prospective ablation이 아니다. 특히 Home Context를
프롬프트에서 제거하는 효과는 이 분석으로 측정할 수 없다.

분석기: `analyze_component_ablation.py`. 입력은 Git에 포함되지 않은
`results/raw_runs.jsonl`(40건)과 `results/heldout_v1/paired/raw_runs.jsonl`(20건)이다.
두 원시 파일의 SHA-256은 각각
`ba6e1e487b730644107290dee0b12bf2bd54c3dba1878c135502897cd45bad5a`,
`6dae7326427558dafbd815c5ef9111c1313f100acb002a7232430da6a9ea431f`이다.
평가셋 SHA-256은 각각
`80bc08ce34a6e280eecd60ecca0c2da354793013f8f53bca27f29f49e3dd6f86`,
`73ec95c9e3c1642606c6e803a0f3f534f0cf8f4cf9d555a885f1c1277e0d4691`이다.
원래 Full Pipeline 실행 커밋은 각각 `d281c9e`, `55e0f15`이고, 두 입력의
모델 digest는 동일한 `a80c4f17acd55265feec403c7aef86be0c25983ab279d83f3bcd3abbcb5b8b72`이다.
두 평가셋의 60개 행은 모두 metric-eligible이고 fallback은 0건이다.

## 재생 방법

각 행에서 LLM의 `parsed_before_normalization`에 해당하는 원출력을 시작점으로
다음 생산 함수 순서를 적용했다.

1. 정규화: 명시 명령과 상황 표현의 결정적 보정
2. 상태 정책: 이미 충족된 커튼 동작의 중복 억제
3. 물리 허용목록: 미배치 장치와 미지원 동작 제거
4. JSON 스키마 검사: 잘못된 구조를 거부하는 검사 단계

순차 적용 결과와 한 단계씩 제거한 결과를 **동일한 고정 원출력**으로 계산했다.
명령 exact match는 `(entity_id, action, value)`의 순서 무관 다중집합 일치다.
스키마 유효성과 오류 건수도 별도로 기록한다. 중간 단계의 명령은 실제 장치에
전송 가능한 결과가 아니다. 스키마 검사는 명령을 수정하지 않으므로, 최종
계획이 모두 유효한 이 표본에서 검사 제거에 따른 점수 차이가 없어도 검사가
불필요하다는 뜻은 아니다.

먼저 원래 최종 출력과 재생된 최종 출력을 **40/40, 20/20 정확히 일치**시켰다.
원래 exact match인 **37/40, 13/20**도 재현됐다. 불일치가 있었다면 아래
분석은 중단하도록 분석기에 검사 조건을 넣었다.

## 결과

| 순차 적용 단계 | 기존 40건 | Prospective 20건 |
| --- | ---: | ---: |
| LLM 원출력 | 8/40 (20.0%) | 5/20 (25.0%) |
| + 정규화 | 30/40 (75.0%) | 7/20 (35.0%) |
| + 상태 정책 | 30/40 (75.0%) | 7/20 (35.0%) |
| + 물리 허용목록 | 37/40 (92.5%) | 13/20 (65.0%) |
| + 스키마 검사 | 37/40 (92.5%) | 13/20 (65.0%) |

순차 비교에서는 정규화가 기존 22건과 prospective 2건을, 물리 허용목록이
각각 7건과 6건을 오답에서 정답으로 바꿨다. 이 순서에서는 정답에서 오답으로
바뀐 사례가 없었다. 상태 정책은 보존된 trace에서 C03, H02, H03의 출력을
바꿨지만, 세 사례의 명령 exact match 성패는 바꾸지 않았다.

| Full Pipeline에서 하나만 제거 | 기존 40건 | Prospective 20건 |
| --- | ---: | ---: |
| 제거 없음 | 37/40 (92.5%) | 13/20 (65.0%) |
| 정규화 제거 | 23/40 (57.5%) | 12/20 (60.0%) |

허용목록 제거 시 미지원 장치 명령은 기존 18개, prospective 26개가 최종
명령에 남았다. 스키마 검사를 제외해도 이 표본의 최종 명령은 모두 유효했다.
원출력에서는 기존 40건 중 1건이 스키마 무효였으나, 후처리를 거친 최종
출력에서는 0건이었다. 검사의 안전 효과는 이 표본만으로 정량화할 수 없다.

## 해석과 사용 경계

기존 평가의 개선은 주로 결정적 정규화와 물리 범위 제한에서 관찰됐다.
반면 prospective 표현에서는 정규화의 추가 개선이 2건에 그쳤고 최종 점수도
13/20이었다. 따라서 구성요소가 새로운 자연어 표현을 모두 회복한다고
주장할 수 없다. 상태 정책과 스키마 검사는 이 표본의 exact match 상승으로
효용을 입증하지 못했으며, 각각 중복 명령 억제와 형식 검증 역할로 설명해야
한다. 안전성이나 실제 물리 제어 신뢰도를 이 표에서 추론하지 않는다.

이 분석은 KICS 제출 이후 수행한 보충 분석이다. 기존 제출 논문의 사전
등록된 실험이나 새로운 prospective 결과로 소급하여 표현하지 않는다.
논문 교체 가능 여부가 확인되기 전에는 제출본의 결과표를 바꾸지 않는다.

재생 결과의 로컬 JSON은 Git-ignored
`results/component_ablation_v1_verified.json`에 보존했고, SHA-256은
`dbdbe9acfc5bddfa98ea9dafa92033bab39e1377ffad9074f33362e4cb3672f1`이다.
Windows에서 행별 결과를 재생하려면 해당 원시 JSONL 두 파일을 비공개로
전달해야 한다. 본 문서의 집계와 분석 코드는 GitHub에 남는다.
